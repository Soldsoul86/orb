# ADR 001: provider-neutral key identity, replaceable service state

2026-10-15. Scope: the standalone private messenger, not Orb's journal/model identity. The uploaded portability mission explicitly authorizes this additive architecture. Existing v1/v2 transport, vaults and libsignal are preserved.

## Baseline

Android Kotlin/Compose, libsignal 0.105.0, Keystore-wrapped atomic vaults, HTTPS Python SQLite/PostgreSQL relay. V2 purpose accounts use bearer capabilities; facet aliases/grants are server-local. No portable control proof, signed routes or encrypted recovery existed. Local baseline: 32 relay tests collected, 30 PASS, socket/PostgreSQL checks skipped by this environment. Android baseline CI 38758117436 PASS (17 JVM, 12 emulator tests). No AGENTS.md in the repository tree; CLAUDE.md, MASTER.md, CONSTITUTION.md, SETTLED.md and apps/veil design/security/contracts were reviewed. No production identity or server will be reset for this proof.

## Candidate comparison

| Candidate | Control/resolution/privacy | Lifecycle/export/interoperability | Mobile/complexity |
|---|---|---|---|
| did:webvh 1.0 | Signed history, self-certifying genesis, optional witnesses; separate DID per purpose. Offline verification possible with complete log; new location still needs discovery | Pre-rotation, update keys and portable rename are specified. Host changes alter DID string while preserving SCID. Requires preserving history and optionally witnesses | Credible open method; more resolver/data-integrity/witness machinery than this proof needs. No mature Android integration already present here |
| did:key 0.9 | Offline key-derived resolution, per-purpose keys possible | No native update/rotation/deactivation. Unacceptable to advertise as a recoverable mutable permanent identity without a separate lifecycle boundary | Small but would not itself solve lifecycle or route discovery |
| RFC 9278 JWK Thumbprint URI + JOSE | Locally generated key identifier, offline public-key verification; no DNS/registry/company dependency. Separate independent controllers per facet | Standard JWK export, JWS signatures and JWE backup. The key identifier is immutable: controller compromise requires a NEW identity and trusted re-enrollment. Operational keys can rotate under the unchanged controller | Nimbus JOSE+JWT (Apache-2.0) supports Java/Android and JCA P-256; independent Python verification uses PyJWT/cryptography. Smallest interoperable key-control proof |

Decision: RFC 9278/RFC 7638 key identifiers, P-256/ES256 JWS and `dir`/A256GCM JWE using established libraries. This is a **key-control identity profile**, not a new DID method, a claim of DID conformance, OAuth conformance, legal identity or a new E2EE protocol. Application policy/route/grant schemas are versioned public contracts. JWS authenticates its exact payload bytes, so no homemade JSON canonicalization/signature scheme is needed. RFC 7638 thumbprints use the library's standard canonical public-key subset.

## Boundaries and lifecycle

Private wallet ownership key never appears in facets, discovery, routes or provider requests. Each facet has an independent exportable controller key and a separate operational device key. Controller keys authorize signed versioned policy/route state; operational keys prove nonce-bound requests. Keys are wrapped by Android Keystore locally; encrypted recovery contains exportable control material. A random 256-bit recovery key protects the JWE package: no weak password and no company-held master key. User must save both separately.

Operational-key rotation removes the old key from current signed state. A stale provider/contact must obtain the newer signed state before rejecting an old operational key; cached highest revision prevents known rollback, not global freshness or split-view attacks. Controller-key rotation under the same fingerprint is impossible and deliberately unsupported. Theft of a controller/recovery package plus its key requires replacement identities and independent contact re-enrollment. No invented cross-signature chain is presented as recovery from a compromised root.

Export includes selected identity controls, policies and authorized relationship bindings, **not message bodies, outbox ciphertext or live Signal ratchets**. Import establishes fresh Signal sessions whose public bundles are authenticated by the same facet controllers; peers explicitly accept the signed route/session change. This avoids cloning active ratchets. Old messages and undelivered Provider-A queues do not migrate. Restoring an old backup may lose recent revocations; recovery cannot determine global latest state without an available witness/peer.

## What must survive Provider A disappearing

The user needs their encrypted export plus separately saved recovery key; the contact needs its pinned facet controller and grants, and a newly signed route card delivered over an independent channel (file/share/QR/paste). Provider B needs only open protocol code, its own database/configuration and the user's signed public state. It never consults A to define identity. Human-readable handles, directory listings and URLs are provider-specific; only the cryptographic controller binding persists. Seamless global lookup of a new route is NOT implemented. Manual delivery of a verifiable route card is the deliberate portable path.
