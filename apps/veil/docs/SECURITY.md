# Threat model and honest boundaries

**Assumption:** two cooperating users on updated, uncompromised Android phones with genuine Veil binaries, secure screen locks, correctly compared identity codes and a working TLS connection. The network and relay may be malicious. The recipient may be careless or deliberately try ordinary capture/export. A malicious recipient controlling their OS or app is outside enforceable client policy.

The controls below are implemented in source. Relay, Linux/JVM native Signal and reveal/expiry policy tests pass; Four selected Android 15 emulator instrumentation tests now pass for unlock/native cover, secure flag and hold/cancel/focus callbacks. OS capture protection and physical verification remain **NOT TESTED / DEVICE REQUIRED**. See STATUS.md for exact evidence. A code path or FLAG_SECURE bit is not evidence that a particular phone blocks capture.

## Android versions and accessibility

Minimum Android 9 / API 28; compiled/targeted at API 35. No Android version or OEM is yet certified by this project. FLAG_SECURE is longstanding, but implementation quality differs. Android 12+ uses `setHideOverlayWindows(true)` and rejects obscured/partly obscured media touches; this does not neutralize accessibility services. API 33+ explicitly disables recents screenshots; older supported versions rely on FLAG_SECURE and exclusion from recents. Android 16+ also requires testing despite targeting 35. Test at least a Pixel and a second vendor's phone, one older supported Android version, and one current version.

On API 28–29 the available biometric/device-credential combination uses BIOMETRIC_WEAK or device credential because strong+credential is unsupported by those BiometricPrompt versions. API 30+ requests BIOMETRIC_STRONG or credential. Device PIN/password enrollment is mandatory. Keystore `setUnlockedDeviceRequired` has platform/version quirks; failures remain locked rather than generating replacement keys. No guarantee of StrongBox or hardware-backed encryption is made.

Protected native media is excluded from the accessibility tree. Hold-only media intentionally has **no accessibility “keep revealed” action**; it may be unusable with some motor aids or TalkBack gestures. This is an unresolved accessibility limitation, not a claim that accessibility is malicious. Navigation and ordinary text remain accessible. A user-enabled accessibility service can read rendered text and control the app. Eyes-Only text is absent until held, but services may observe it during reveal. Some secure-window screenshot APIs will fail while semantic extraction still works. The app does not disable or secretly monitor accessibility services.

Trusted input methods are necessary. Autocorrection is disabled, but third-party keyboards can still observe typed content and invitations. Received text has no selectable UI. Protection does not reach into the system picker, share sheet or external invitation channel. Source photos/videos in the sender's gallery are not deleted or made private by sending them.

## Watermark and deletion claims

The watermark contains a pseudonymous key fingerprint fragment, a message marker and UTC time, not a legal name, telephone number, location or email. It repeats with slow sinusoidal drift and translucent text/shadow. Opacity, readability, contrast and crop resistance are **not physically evaluated**. An honest recipient's mark is a reminder of intended audience. A captured image is not trustworthy evidence of who leaked it; the mark can be fabricated or altered.

Disappearance means cooperating app UI hides expired messages and later removes their encrypted records; relay queues delete expired blobs. It does not remotely erase recipient copies, source-gallery files, screenshots, photographed displays, prior backups, malicious relay copies, filesystem snapshots or flash remnants. Secure deletion cannot be guaranteed on flash or SQLite WAL. The whole-vault key persists, so an old encrypted snapshot plus access to that key may reveal old content. Media opening limits can be bypassed by clock rollback across restarts, restore or patched software. We do not market cryptographic erasure.

## Unresolved risks / release gates

- No successful Android build, install, native crypto test or runtime lifecycle test in this workspace. Compatibility errors may remain despite checking upstream API source.
- No independent audit of key storage, session persistence, authentication integration or application envelope validation. Protocol reputation does not replace integration review.
- No prekey rotation, inbox renewal/revocation UI, account recovery, device replacement, remote wipe or multi-device sync.
- Polling only while foreground/unlocked; failed writes and poison envelopes can delay reception. Registration throttling is process-local. Internet-scale abuse protection is absent.
- Inline media and full-vault reads need memory/battery profiling; low-memory crashes must not reset keys. Native codecs handle attacker-supplied media, so security updates matter.
- Release signing, dependency checksum verification, supply-chain review, licensing packaging and update distribution remain to be done before distribution.
