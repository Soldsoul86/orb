# Guest entry decision — 2026-10-21

Status: RELEASE BLOCKED. This directory is an isolated, disabled development foundation, not working guest messaging. No production route, APK identity, grant or encryption behavior changes.

Product: camera → HTTPS contact page → optional name + text → one encrypted request → owner approval → two-way browser/native text → optional install offer after a decrypted reply. No account or identity-code comparison on entry. No browser capture-protection claim. No background notification or automatic APK handoff claim.

Compatibility: pi/1 currently uses owner-controlled ES256 JWS state, per-contact controller-signed Signal bundles, nonce-bound operational proofs, scoped signed grants and libsignal 0.105.0 PQXDH/ratcheting envelopes. Keep all of these. The official TypeScript distribution is a native Node addon, not a browser implementation. The old official browser library is archived. Community WASM wrappers require review and exact-version interoperability work; their upstream cryptography does not establish the security of the bridge, storage or Veil integration. Matrix/Olm and MLS are standards-based alternatives requiring a separately versioned Android guest channel, not drop-in Signal substitutes. See CRYPTO_COMPATIBILITY.md.

Trust: the QR must pin a purpose controller independently of the resolving server. A proposed /g/<RFC7638-thumbprint> address provides a public per-purpose pin; an optional fragment contains a request-only unlisted invitation reference. Neither grants chat access or possesses a guest identity. Reusable addresses have no unlisted fragment and require explicit public/link-only owner policy. Existing /i#token links do not carry a pin and must not silently become server-substitution-resistant guest links. Forwarding a link permits requests only. No global wallet key, recovery secret or correlation identifier is exposed. This parser/verification foundation is not yet emitted by Android or resolved by the live service.

A future guest generates its own purpose-local controller/device keys and Signal material in-browser, never at the provider. It proves key possession using the existing signed nonce/command profile. Store the minimum ratchet/outbox atomically before network, receive/deduplicate before ack; no second send before a verified approval. Persist encrypted browser state with a nonextractable Web Crypto wrapping key where supported; same-origin malicious JS can still use that key. Clearing storage loses the session. This persistence/send path is NOT implemented while crypto is blocked.

The relay stores ciphertext, public state, grants, request timing and bounded routing metadata. Keep invitation validity, pending-request lifetime and accepted-grant lifetime distinct. Existing provider enforcement (approval, office hours, rate/size limits, nonce replay and revocation) stays authoritative; UI state is not authorization. A dedicated public-web origin is required before release. CSP cannot protect a guest against an actively compromised server replacing the JS delivered on first load: distinguish passive relay/database compromise from malicious web-code delivery. Public launch needs an explicit web-code trust review, audited adapter/integration and passing browser↔Android proof. No claim of zero metadata or prevention of copied content.

Current implementation: strict address parser; existing ES256/JOSE public-statement verification using Web Crypto; request-state presentation model; accessible isolated entry UI; loopback-only read-only development server rejecting every mutation before body parsing; tests and CI. The send adapter always throws, the server has no messaging endpoint, and deployment gate exits nonzero. No env variable can enable messaging. Synthetic UI tests are labeled UI-only and never count as message delivery.

Portability: owner keys remain user-held; a new provider requires the existing independently delivered signed route card. Human-readable URLs do not follow migration automatically. Guest restoration/handoff and reusable/one-time invitation persistence are not implemented. No production migration or paid resource is needed for this disabled foundation.
